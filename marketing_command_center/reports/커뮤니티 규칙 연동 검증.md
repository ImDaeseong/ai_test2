# 외부 HOLD를 검증 가능한 단계로 전환한다

Marketing Command Center의 남은 HOLD는 기능 부족을 숨긴 실패가 아니라, **로컬 소프트웨어가 대신 증명할 수 없는 세 종류의 외부 사실**이다. 실제 독자 반응은 사전 등록한 소규모 실험과 원시 성과 데이터로, 커뮤니티 규칙 준수는 대상 게시판의 공지 URL·확인일·검수자 승인으로, API 게시 준비는 OAuth 동의·계정 역할·플랫폼 심사·최소 권한 live 응답으로 각각 검증해야 한다. 제품은 이 세 증거를 한 개의 `게시 가능` 상태로 뭉치지 말고 자동 검사, 사람 확인, 외부 승인 상태를 분리해야 한다. 로컬에서 확인 가능한 구성과 문안 위험 신호는 자동화하되, 실제 승인이나 반응을 추정해서 PASS로 올려서는 안 된다. Threads·Instagram·X·LinkedIn·Naver Cafe는 공식 연동의 조건이 서로 다르며, **Naver Blog 자동 쓰기는 공식 Open API가 종료되어 수동 인계만 지원해야 한다**. 본 보고서는 2026-10-22에 확인한 공식 자료를 기준으로 구현 경계와 우선순위를 제안하며, 실제 게시·계정 승인·독자 효과가 이미 검증됐다고 주장하지 않는다.

## 하나의 준비도 대신 세 증거 축을 기록한다

현재 HOLD를 줄이는 가장 중요한 개선은 `연결됨`, `규칙 준수`, `성과 있음`을 서로 독립된 축으로 모델링하는 것이다. 토큰이 있다고 커뮤니티 규칙을 준수한 것은 아니고, 규칙을 사람이 확인했다고 OAuth 쓰기 권한이 생긴 것도 아니며, 게시 성공이 독자의 반응을 입증하지도 않는다. 제품은 각 게시 후보에 `content_check`, `community_review`, `provider_readiness`, `audience_evidence`를 따로 저장하고, 최종 상태는 네 축 가운데 가장 약한 증거를 정직하게 드러내야 한다. LinkedIn은 원치 않는 홍보와 과도한 반복 콘텐츠를 금지하고, 네이버 역시 동일·유사 홍보 게시의 반복과 무허가 자동화를 제한하므로, 단순히 API 요청이 성공했다고 운영 적합성을 판정할 수 없다. ([LinkedIn Professional Community Policies](https://www.linkedin.com/legal/professional-community-policies); [NAVER 게시물 운영정책](https://policy.naver.com/policy/service_group.html))

| 증거 축 | 자동화 가능한 검사 | 반드시 사람이 남길 증거 | live 외부 전제조건 | 정직한 미완료 상태 |
|---|---|---|---|---|
| 문안·안전 | 유사 문안, 반복 URL, 과장·보장 표현, 과도하거나 무관한 해시태그, 개인정보 패턴, 광고·AI 미디어 표시 누락 가능성 경고 | 주장 근거, 이미지·후기·상표 권리, 등장 인물 동의, 의료·자격 표현, 경제적 이해관계 표시 적절성 | 없음 | `HOLD_HUMAN_CONTENT_REVIEW` |
| 커뮤니티 규칙 | 공지 URL 형식·접근일·만료일 존재, 필수 체크박스 완결성, 검수 후 문안 변경 감지 | 대상 커뮤니티와 게시판, 공지 URL, 확인 시각, 검수자, 허용 게시판·말머리·링크·연락처·빈도·지역/연령 제한 | 실제 가입 및 글쓰기 등급, 운영자 승인이나 게시판 권한 | `HOLD_RULES_UNVERIFIED` |
| 계정·API | 환경변수 이름의 존재 여부, HTTPS redirect URI, 선언 scope, 토큰 저장소 경계, 중복 방지 키, 미리보기·명시적 확인 단계 | 계정 소유자, 동의 시각, 앱/페이지/조직 역할, 심사 증거 ID, 시험 게시 승인 및 삭제 계획 | 개발자 앱, OAuth 동의, 유효 토큰, 요구 역할·제품 접근·심사 | `CONSENT_REQUIRED`, `REVIEW_REQUIRED`, `TOKEN_NOT_TESTED` |
| 실제 독자 반응 | 실험 계약 검증, 문안 해시, 데이터 완결성, 분자·분모 계산, 안전 중단 신호, A/B 외 변경 탐지 | 가설·주지표·기간의 사전 승인, 게시 URL/ID, 실제 반응 데이터의 출처 확인 | 실제 계정 게시, 충분한 노출, 플랫폼 분석 화면 또는 승인 API | `HOLD_DATA_QUALITY`, `HOLD_INSUFFICIENT_EXPOSURE`, `HOLD_NOISY` |

자동 문안 검사는 위반을 확정하는 판사가 아니라 검수 대상을 좁히는 경보다. Instagram과 Threads의 공통 정책 기반은 반복 콘텐츠, 동의 없는 상업 연락, 가짜·오도성 리뷰, 무권리 미디어를 제한하고, X도 대량·중복·무관 게시와 인위적 참여 조작을 금지한다. 하지만 `반복적`, `원치 않는`, `무관한`에는 모든 계정에 적용되는 공식 숫자 임계값이 없으므로 제품이 임의의 게시 횟수나 해시태그 수를 플랫폼 한도로 표시하면 안 된다. ([Instagram Community Guidelines](https://www.facebook.com/help/477434105621119?locale=en_GB); [X Authenticity Policy](https://help.x.com/en/rules-and-policies/authenticity)) 검사 결과는 `경고 코드 + 근거 정책 URL + 사람이 확인할 질문`으로 표시하고, 문맥·사실성·권리·동의·지역 법률은 항상 사람 HOLD로 남겨야 한다.

## 실제 반응은 작은 승리보다 재현 가능한 기록이 먼저다

독자를 끄는 문안인지 검증하려면 먼저 성공의 의미를 고정해야 한다. 게시 전에 `experiment_id`, 채널, 대상 커뮤니티, 가설, 기준 문안 A, 변형 B, **한 가지 변경 변수**, 주지표, 보조지표, 안전 가드레일, 시작·종료 시각을 저장하고 이후 수정할 수 없게 잠가야 한다. NIST는 비교·반복·무작위화·통제·대표성·블로킹을 실험 설계의 핵심으로 설명하고, GOV.UK는 표본과 기간을 실제 트래픽 및 기대 변화에 맞춰 사전에 정하고 결과가 불명확하면 결론을 강요하지 말라고 권한다. ([NIST Technical Note 2340](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=959904); [GOV.UK A/B testing guidance](https://www.gov.uk/guidance/ab-testing-comparative-studies)) 따라서 제품은 작은 관찰에서 임의의 `통계적으로 유의`, `승자`, `전환율 개선` 문구를 생성하지 않아야 한다.

사람이 입력하거나 승인된 API에서 수집할 최소 증거는 `post_id/url`, 문안 버전과 해시, 게시자·승인자, 게시 및 관찰 시각, 채널·커뮤니티, 노출 또는 도달, 사전 지정 CTA 행동 수, 댓글·공유·저장·반응 수, 삭제·신고·부정 댓글·운영자 경고, 수집 출처, 수집 시각, 누락·오류 상태다. Meta의 공식 A/B 도구도 핵심 지표 하나를 먼저 선택하고 댓글·공유·반응·도달·링크 클릭 등을 후보로 제시한다. ([Meta Business Help Center](https://z-p4-lookaside.fbsbx.com/business/help/1675344823455042)) 제품 화면은 비율만 보여주지 말고 `A: 1/20, B: 2/18`처럼 원시 분자와 분모를 함께 보존해야 하며, 노출을 얻지 못한 경우 0%가 아니라 `NOT_MEASURED`로 기록해야 한다.

판정 순서는 **데이터 무결성 → 안전 → 비교 가능성 → 증거량 → 관찰 방향**이어야 한다. 게시 ID나 분모가 빠지면 `HOLD_DATA_QUALITY`, 규칙 위반·개인정보 노출·의료 효능 오인·신고가 확인되면 `SAFETY_STOP`, 시간대·대상·채널 등 여러 변수가 함께 바뀌면 `HOLD_NOISY`, 비교 가능한 반복이 부족하면 `HOLD_INSUFFICIENT_EXPOSURE`, 사전 조건을 충족했지만 개선이 관찰되지 않으면 `NO_LIFT_OBSERVED`로 분류한다. 자연 게시에서 이용자를 무작위 배정할 수 없다면 실험을 `QUASI_EXPERIMENT`로 표시한다. **현재는 실제 게시 노출과 반응 데이터가 없으므로 독자 효과는 여전히 미검증 상태**이며, 구현 가능한 것은 이 증거 계약과 허위 승리 선언을 막는 상태 기계다.

## 규칙 검수는 게시판 단위로 만료된다

플랫폼 공통 정책을 읽은 것만으로 특정 네이버 카페나 LinkedIn 그룹의 게시 허용을 증명할 수 없다. 네이버는 카페·블로그 특성상 홍보 기준을 일부 완화하지만 세부 제한이 서비스마다 다를 수 있다고 밝히고, 카페 운영진은 게시판별 읽기·댓글·글쓰기 권한을 설정할 수 있다. ([NAVER 홍보성 게시물](https://help.naver.com/service/19212/contents/7997?lang=ko&osType=COMMONOS); [NAVER 카페 게시판 권한 설정](https://help.naver.com/service/5622/contents/15704?lang=ko&osType=PC)) 그러므로 규칙 검수 레코드에는 플랫폼 이름이 아니라 `community_id`, `board_id`, 공지 URL, 원문 제목 또는 해시, 확인일, 검수자, 가입·글쓰기 등급, 홍보/모집 허용 여부, 말머리·제목 형식, 외부 링크·연락처, 게시 빈도, 교차 게시, 지역·연령·자격 제한을 저장해야 한다.

이 레코드에는 유효기간과 무효화 조건도 필요하다. 확인일로부터 팀이 정한 재검토 기간이 지나거나, 게시판이 바뀌거나, 공지 URL 또는 원문 해시가 달라지거나, 검수 뒤 문안의 링크·가격·대상·보상 조건이 바뀌면 상태를 즉시 `HOLD_RULES_UNVERIFIED`로 되돌린다. 다만 재검토 기간은 제품 운영 정책이지 플랫폼이 보증한 공식 주기가 아니므로 UI에 그 차이를 표시해야 한다. 네이버 카페 API는 가입 등급·메뉴 제한·금칙어·스팸 차단 때문에 403을 반환할 수 있으므로, API 오류를 규칙 준수 증거로 해석하지 말고 권한/규칙/스팸 가능성을 구분해 사람에게 보여줘야 한다. ([NAVER 카페 가입·글쓰기 API](https://developers.naver.com/docs/login/cafe-api/cafe-api.md))

게시 전 승인 화면에는 자동 경고와 별도로 `주장 증빙`, `전문 자격·의료 표현`, `사진·후기·상표 사용권`, `등장 인물 동의`, `대가·협찬·무료 조건`, `개인정보와 연락 동의`, `커뮤니티 관리자 규칙`, `지역 광고·경품·업종 법률`, `최근 게시물과의 반복성`, `링크 최종 목적지`, `AI 생성 미디어 표시`를 검수자 확인란으로 제공해야 한다. 공정거래위원회는 제3자의 독립적 의견처럼 보이는 추천·보증에 경제적 대가가 있다면 그 관계를 공개해야 한다고 안내한다. ([공정거래위원회 경제적 이해관계 표시 안내](https://www.ftc.go.kr/DATA/download/www/cts304_file.pdf)) 체크박스만 클릭하는 형식적 승인을 막기 위해 각 승인에는 검수자, 시각, 근거 링크 또는 증빙 참조, 대상 문안 해시를 결합하고, 문안 변경 시 승인을 폐기해야 한다.

## 자동 게시는 공급자별 관문 뒤에서만 열린다

API 게시 기능은 공통 인터페이스를 만들기 전에 공급자별 준비 상태를 정확히 나눠야 한다. Threads는 Meta 앱의 Threads 사용 사례, OAuth 동의, `threads_basic`과 `threads_content_publish` 등 필요한 범위, 토큰 수명주기와 게시 호출이 필요하다. Instagram은 선택한 로그인 방식에 맞는 Meta 앱과 Professional 계정이 필요하며, Facebook Login 방식에서는 Page 연결과 `instagram_content_publish` 등 관련 권한이 요구되고 일반 소비자 계정은 지원되지 않는다. ([Meta Threads API collection](https://www.postman.com/meta/threads/documentation/dht3nzz/threads-api); [Meta Instagram API collection](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api)) Meta 개발자 원문은 2026-10-22 조사 당시 자동 접근에 429를 반환했기 때문에 이 요건은 Meta 공식 Postman 컬렉션으로 확인했으며, App Review·Advanced Access 적용 여부는 실제 앱 대시보드에서 다시 확인해야 한다.

X는 승인된 Project/App, 사용자 컨텍스트 OAuth와 쓰기 권한이 필요하며, 403은 endpoint 접근 또는 권한 부족, 429는 rate/post cap을 뜻할 수 있다. 게시 API는 유료 파트너십 및 AI 생성 미디어 공개 필드를 지원하지만, 실제 보상 관계와 미디어 생성 방식은 사람이 제공해야 한다. ([X Create Posts API](https://docs.x.com/x-api/posts/create-post); [X API error guidance](https://developer.x.com/en/support/twitter-api/error-troubleshooting)) LinkedIn 개인 게시에는 회원의 3-legged OAuth 동의와 `w_member_social`이 필요하고, 조직 게시에는 `w_organization_social`, 조직 URN, 허용된 Page 역할과 Community Management 제품 접근이 별도로 필요하다. ([LinkedIn API access](https://learn.microsoft.com/en-us/linkedin/shared/authentication/getting-access); [LinkedIn Posts API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api); [LinkedIn Community Management App Review](https://learn.microsoft.com/en-us/linkedin/marketing/community-management-app-review?view=li-lms-2026-05)) 실제 Developer Portal 승인 증거 없이는 조직 게시를 READY로 표시하면 안 된다.

Naver Cafe는 앱 등록, Client ID/Secret, API 권한, Naver Login OAuth 동의, `clubid/menuid`, 해당 회원의 가입·게시판 쓰기 권한을 요구하므로 공식 API 연동 후보가 될 수 있다. 반면 **Naver Blog 외부 글쓰기 Open API는 2020-05-06 종료되었다**. ([NAVER Cafe API](https://developers.naver.com/docs/login/cafe-api/cafe-api.md); [NAVER 블로그 Open API 종료](https://developers.naver.com/notice/article/7527)) 따라서 Naver Blog에 비공식 브라우저 자동화나 숨은 endpoint로 우회 게시하는 경로는 `UNSUPPORTED`로 고정하고, `본문 복사 → 공식 작성 화면 열기 → 사용자 직접 게시`만 지원해야 한다. 공식 Open API 목록 역시 게시 기능으로 Cafe를 열거하고 Blog는 검색 API만 열거한다. ([NAVER Open API list](https://developers.naver.com/docs/common/openapiguide/apilist.md))

모든 공급자는 `LOCAL_READY → CONSENT_REQUIRED/REVIEW_REQUIRED → TOKEN_NOT_TESTED → LIVE_READ_PASS → LIVE_WRITE_PASS` 순서로 승격한다. `LOCAL_READY`는 환경변수 이름, HTTPS redirect URI, scope 선언, OS 비밀 저장소 참조, 명시적 최종 확인, idempotency key, 감사 로그 설계가 갖춰졌다는 뜻일 뿐 게시 가능을 뜻하지 않는다. `LIVE_READ_PASS`는 토큰과 계정 ID를 노출하지 않은 최소 권한 프로필 호출로 검증하고, `LIVE_WRITE_PASS`는 **계정 소유자가 대상·문안·공개 범위·삭제 계획을 명시적으로 승인한 뒤에만** 삭제 가능한 테스트 게시와 정리까지 성공했을 때 부여한다. 실제 자격 증명, 소유자 동의, 앱 심사 결과가 제공되지 않은 현재 상태에서 live 게시를 실행하거나 승인을 만들어내서는 안 된다.

## 네 단계 구현이 위험과 효과를 함께 줄인다

첫 번째 우선순위는 상태 모델과 증거 스키마를 분리하는 일이다. 자동 PASS 한 칸을 없애고 위 네 증거 축, 세부 HOLD 코드, 문안 해시 기반 승인 무효화, 비밀값 비노출을 먼저 구현해야 한다. 두 번째는 게시 전 규칙 패키지다. 공식 공통 정책에서 유도한 정적 경고, 커뮤니티 공지 URL·확인일·검수자·게시판별 제약, 승인 만료와 문안 변경 가드를 구현하면 실제 계정 없이도 가장 큰 허위 완료 위험을 줄일 수 있다. 세 번째는 반응 실험 레지스트리다. 사전 등록, 단일 변경 변수, 원시 분자·분모, 데이터 품질 및 안전 중단 상태를 갖춘 뒤 실제 소규모 게시를 사람이 승인하도록 한다.

네 번째이자 마지막 우선순위가 공급자 API 어댑터다. 먼저 최소 권한 읽기 검증을 구현하고, Threads·Instagram·X·LinkedIn 개인·LinkedIn 조직·Naver Cafe를 서로 다른 능력과 오류 분류로 다룬다. 그 뒤 계정 소유자 동의와 플랫폼 준비 증거가 있는 공급자만 삭제 가능한 시험 게시로 승격한다. Naver Blog는 이 순서에 포함하지 않고 영구 수동 경로로 둔다. 이 우선순위는 계정 심사를 기다리는 동안에도 문안 안전·규칙 준수·실험 증거의 품질을 높이며, 나중에 OAuth를 붙였을 때 `API가 작동한다`를 `게시해도 된다`로 오인하는 구조적 결함을 예방한다.

## Conclusion

남은 HOLD를 없애는 목표보다 **HOLD가 어떤 외부 증거로만 해제되는지 기계적으로 명확하게 만드는 것**이 먼저다. 이 경계를 구현하면 Marketing Command Center는 외부 승인을 조작하지 않으면서도 준비 부족, 사람 검수 대기, 공급자 승인 대기, 실제 반응 부족을 서로 다른 다음 행동으로 바꿀 수 있다.

출시 판단에서 가장 의미 있는 변화는 자동화 비율이 아니라 증거의 출처가 보존되는 것이다. 문안 해시와 검수 근거, 게시 ID와 원시 반응, OAuth 계정과 scope, 심사 증거가 각각 연결되어야만 실제 독자 효과와 플랫폼 적합성을 나중에 재검증할 수 있다. 그 전까지 수동 게시 경로는 임시방편이 아니라, 특히 Naver Blog에서 공식적으로 지원되는 정직한 제품 경계다.
