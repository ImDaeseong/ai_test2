Threads 연동 설계 구조

Threads 전용 규칙을 독립 모듈에 가두고, 검증된 계약만 나중에 marketing_command_center와 연결합니다.

설계 원칙

변경 격리

Threads 엔드포인트와 파라미터는 어댑터 밖으로 노출하지 않습니다.

성공 증거

컨테이너 ID가 아니라 게시물 ID와 최종 상태로 완료를 판정합니다.

비밀 분리

토큰 저장소를 게시 내용과 분리하고 로그에서 비밀값을 제거합니다.

변경 HOLD

공식 계약이 달라지면 회귀 검증 전까지 자동 적응으로 가장하지 않습니다.

컴포넌트 경계

교육 CLI 또는 marketing_command_center │ 공통 PublishRequest ▼ 게시 오케스트레이터 │ Threads 전용 요청 ▼ ThreadsAdapter ┌─────────┼──────────┐ ▼ ▼ ▼ TokenVault MediaURL Threads API │ │ └────┬─────┘ ▼ 상태·증거 저장소

marketing_command_center는 media_type이나 creation_id를 직접 만들지 않습니다. 공통 의도만 전달하고 변환과 오류 해석은 어댑터가 담당합니다.

입력과 결과 계약

PublishRequest

request_idchannelaccount_idtextmedia_refs[]link_urlalt_textidempotency_key

media_refs는 로컬 경로가 아니라 내부 미디어 식별자입니다.

PublishAttempt

stateprovider_container_idprovider_post_idprovider_trace_iderror_classtimestamps

게시물 ID와 최종 상태가 있어야 PUBLISHED입니다.

상태 흐름

1

DRAFT → QUEUED

사용자 승인과 작업 등록 단계입니다.

2

CREATING_CONTAINER → PROCESSING

Threads가 내용을 접수하고 미디어를 처리합니다.

3

PUBLISHING → PUBLISHED

준비된 컨테이너를 게시하고 원격 게시물 ID를 저장합니다.

중단 상태: REAUTH_REQUIRED, FAILED_PERMANENT, HOLD, CANCELLED, UNKNOWN_OUTCOME

향후 통합 순서

  1. 텍스트 한 건을 OAuth부터 원격 조회까지 실제 검증합니다.
  2. 이미지·영상 임시 URL의 수명주기를 붙입니다.
  3. 캐러셀과 상태 폴링을 추가합니다.
  4. outbox, 작업 큐, 중복 방지와 재조정을 추가합니다.
  5. 마지막에 marketing_command_center가 공통 요청을 만들도록 연결합니다.

사람 검토 HOLD

앱 승인, 실제 OAuth, 유형별 실게시, 최신 미디어 규격, 웹훅 서명·재전송, 개인정보·저작권 정책은 실제 증거와 사람 승인이 필요합니다.
